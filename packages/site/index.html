01 The problem 4 FAILURE MODES

Every AI tester will happily tell you
it found nothing.

The hard part was never generating tests. It is knowing whether to believe the report. Four ways the confident summary on your screen is wrong:

  • 01

    It never clicked anything

    The agent describes a flow it did not run. There is no trace, no spec, no screenshot, and prose costs nothing to fabricate.

  • 02

    Its own selector was wrong

    The test failed because the agent guessed the wrong locator, and the app gets blamed for a bug that does not exist.

  • 03

    The specs were skipped

    Zero tests executed. The summary still reads green, because nobody was counting what did not run.

  • 04

    It looked at six things

    Then reported "all clear". This one is unfixable by any amount of verification, so Clarvis measures it instead of hiding it.

02 How it works 2 FLEETS · 1 CONTRACT

Two fleets. One contract.

Researchers learn the project and write a single file. Testers read only that file. Nothing project-specific lives anywhere else, which is why the same fleet works on the next codebase without being rewritten.

  1. 01

    Recon

    Six researchers boot the app for real, log in as every role, map the routes, detect the stack, and rank the risk. They write .clarvis/profile.json. If they cannot prove the app starts, the pipeline stops and asks you a question instead of guessing.

    WRITES PROFILE
  2. 02

    The fleet

    Seven axes, each with its own browser process and its own obsession: happy path, permissions and scope, adversarial input, i18n and RTL, responsive and a11y, resilience, visual. They write real Playwright specs. Not opinions, files.

    7 AXES
  3. 03

    Triage

    A separate agent, given only the artifacts, tries to reproduce each finding cold. Three times. Then runs it against the parent commit to prove the spec is not the thing that is broken.

    3/3 COLD
  4. 04

    What you keep

    Confirmed findings, and the deterministic spec files behind them. Promote those into CI and they keep working long after the run is forgotten. The report is disposable. The suite is the asset.

    OUTPUT
03 Why you can believe it 6 GATES

Six ways a finding dies
before it reaches you.

Not one of these is an agent judging its own work. Every gate is deterministic code, or a different agent that never saw the original claim.

01 No artifact, no finding

A claim without a rerunnable spec and a trace is discarded by tooling. Not judged. Discarded.

02 Numbers come from the runner

Pass, fail and skip are parsed from the test reporter's own JSON. No agent can narrate around them, and skipped is treated as an alarm.

03 Cold reproduction, 3 of 3

A different agent, handed only the spec, must reproduce it three times from a cold browser. Two of three is a flake, and gets filed as one.

04 Negative control

The same spec runs against the parent commit. Failing there too means the spec is wrong, not your app.

05 An oracle, cited

Every finding names its source of truth: a spec line, an i18n key, a visible label. No citation caps it at "question", never "bug".

06 Assertion lint

Generated specs are scanned for tests that cannot fail. An agent cannot weaken its own assertion until the run turns green.

04 Safety FAILS CLOSED

It refuses, by default.

A tester pointed at the wrong host can write junk into production. So the decision to mutate anything is made by plain deterministic code, before a single browser opens, and it fails closed at every branch.

  • Unvetted projects are read-only. Mutating axes run only when a human has explicitly marked the target disposable. The default is false, so silence means no.
  • A deny-list beats everything. Name your production hosts once. A match aborts the entire run, even if the allow-list would have permitted it.
  • Nothing leaves the machine. Clarvis installs locally and drives your app locally. Your source is never uploaded, because there is no server to upload it to.
  • Refusals are loud. Every axis the guard blocked is listed in the run. A partial pass is never presented as full coverage.

05 Honest limits DISCLOSED

What Clarvis will not claim.

False positives are solvable.

Six verification passes push them close to zero. The cost is throughput: every finding is run roughly six times before you see it. That trade is deliberate.

False negatives are not.

No amount of verification catches the bug nobody looked at. So Clarvis never shows a verdict without coverage beside it, and prints an explicit list of everything a run did not cover.

No detection rate. Yet.

Publishing one requires a seeded-bug benchmark measuring how many known bugs the fleet actually finds. That work is in progress. Until it ships, any percentage would be marketing, not measurement.

Use Clarvis as a wide net and a regression-suite generator. Not as sign-off. You still sign off.
